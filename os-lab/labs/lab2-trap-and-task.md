## 一、问题场景

Lab1 结束时，你已经有了一个能开机、打印 `Hello, OS!`、关机的内核。但现在它有个尴尬的局限：**它只会自言自语**。所有输出都是内核自己写死的，它不能运行"用户程序"，更不能同时管几个程序。

想象一下，如果你是操作系统的设计者，现在要让这个内核"能干活"，你会立刻撞上几个绕不开的问题：

- **程序该怎么和内核说话？** 假设你想写一个用户程序在屏幕上打印一行字。但用户程序运行在低特权（U-mode），它**没有权限直接写屏幕**（屏幕是硬件，碰硬件要高特权）。那它凭什么让屏幕亮起来？——它得"请求"内核代劳。可这个"请求"具体是个什么动作？内核又怎么知道它是来求助的，而不是触发了错误？
- **切换的一瞬间，数据怎么办？** 当用户程序发出请求、CPU 从用户态切到内核态的那一刻，用户程序所有的寄存器都装着它正在计算的中间结果。如果内核不把这些保存好，等它处理完返回时，用户程序就拿不回原来的状态，直接崩溃。可保存到哪里？用什么节奏保存？
- **多个程序怎么轮流用 CPU？** 如果同时有好几个程序，总不能让第一个程序独占 CPU 跑到底、后面的永远等着。内核得有办法在它们之间切换。但"切换"具体意味着什么？切换时每个程序的状态记在哪？

这三个问题——**怎么陷入、怎么保存、怎么调度**——是任何操作系统内核的核心机制。本实验会带你走通这条路：让内核加载并运行 3 个用户程序（`hello`/`power`/`yield`），通过系统调用与它们交互。

> 建议的学习方式：每个小节先停下来想"**如果是我，会怎么解决**"，再往下读看实际的机制是怎么做的。带着自己的猜测对照，比被动接受理解得深得多。

## 二、背景知识

### 2.1 特权级与 trap

RISC-V 有多个特权级，本实验关心两个：

```mermaid
graph LR
    U["U-mode 用户态<br/>用户程序运行"] -->|"ecall 陷入"| S["S-mode 内核态<br/>内核运行"]
    S -->|"sret 返回"| U

    classDef umode fill:#e3f2fd,stroke:#1565c0,stroke-width:2px;
    classDef smode fill:#ffebee,stroke:#c62828,stroke-width:2px;
    class U umode;
    class S smode;
```

- **U-mode（用户态）**：用户程序运行的模式，权限受限，不能直接访问硬件或内核内存。
- **S-mode（监督态）**：内核运行的模式（lab1 就在这里），权限较高。
- **trap（陷入）**：从低特权转到高特权的过程。触发 trap 的原因有两类：
  - **系统调用**：用户程序主动执行 `ecall` 指令，请求内核服务。
  - **异常/中断**：程序出错（如非法地址）或外部事件（如时钟中断）。

内核通过 `scause` 寄存器判断 trap 的具体原因，再做相应处理。

### 2.2 上下文保存与恢复

> 🤔 **先停一下想**：如果你是内核设计者，用户程序发出 `ecall` 的那一瞬间，它的 32 个寄存器里都装着正在计算的中间结果。等内核处理完要返回用户态时，这些值必须原封不动地还回去。你会把这些寄存器存到哪？存多少个？存的时候要注意什么？

trap 发生时，CPU 从用户态切到内核态，但**用户程序的寄存器状态不能丢**——否则返回后程序没法继续。内核必须先把所有通用寄存器（x0-x31）和几个关键 CSR（`sstatus`、`sepc`）保存到一个结构体里，这个结构体就是 **TrapContext**。

```mermaid
graph TD
    A["用户态运行中"] -->|"ecall/中断"| B["硬件自动: 切 S-mode<br/>PC 存入 sepc"]
    B --> C["__alltraps: 保存 32 个 GPR<br/>+ sstatus + sepc 到 TrapContext"]
    C --> D["trap_handler: 根据 scause 分发<br/>处理系统调用/中断"]
    D --> E["__restore: 从 TrapContext 恢复<br/>所有寄存器"]
    E --> F["sret 返回用户态"]

    classDef save fill:#fff3e0,stroke:#ef6c00;
    classDef restore fill:#e8f5e9,stroke:#2e7d32;
    class C save;
    class E restore;
```

保存和恢复的**顺序必须严格对应**（保存的第 N 个寄存器，恢复时也要取第 N 个），否则用户程序会拿到错的值。这一步必须用汇编做（`trap.asm`），因为此时还没有可用的栈、不能调用任何函数——Rust 函数调用本身就要用栈和寄存器，会破坏我们要保存的状态。

### 2.3 两个栈的切换：`sscratch` 的妙用

> 🤔 **再想一个更难的**：上一步说要"保存寄存器到栈上"。但 trap 发生的瞬间，`sp` 寄存器指向的是**用户栈**。内核不能往用户栈写（会破坏用户数据，且用户栈可能根本没映射）。那内核怎么拿到自己的栈？——你能在不破坏任何寄存器的前提下，拿到内核栈吗？

这是个"鸡生蛋"难题：要保存 `sp` 就要用栈，要用栈就要先有内核栈，要拿内核栈又得有个地方临时存用户栈……解法是 **`sscratch` 寄存器**——它是 RISC-V 提供的一个"便签"寄存器，平时保存着内核栈指针。

trap 入口的第一条指令是 `csrrw sp, sscratch, sp`：把 `sp`（用户栈）和 `sscratch`（内核栈）**交换**。这一条指令同时完成了两件事——"把用户栈存进 sscratch 保管"和"把内核栈装进 sp 供后续使用"，而且不经过任何其他寄存器。这是整个 trap 机制里最巧妙的一步，值得反复体会。

### 2.4 系统调用的约定

> 🤔 **先想**：假设内核和用户程序已经能 trap 切换了。那内核怎么知道用户这次是"要写屏幕"还是"要退出"？又怎么拿到用户给的参数（比如要写的内容、长度）？——你需要一套**约定**：哪个寄存器放"服务编号"、哪些放参数、哪个放返回值。

RISC-V Linux ABI 就是这么一套约定（操作系统圈通用的"普通话"）：

- `a7`（x17）：系统调用号（告诉内核"我要哪个服务"）
- `a0`-`a6`（x10-x16）：参数
- `a0`（x10）：返回值

本实验用到的系统调用（编号定义在 `os-syscall`，遵循 Linux 约定）：

| 编号 | 名称 | 用途 | 参数 |
|------|------|------|------|
| 64 | `sys_write` | 写入（本实验用于屏幕输出） | fd, buf, len |
| 93 | `sys_exit` | 退出程序 | exit_code |
| 124 | `sys_yield` | 主动让出 CPU | 无 |

> 想清楚这套约定后，你就能在脑中走通一条链路：用户把参数塞进 a0-a2、服务号塞进 a7、执行 `ecall` → trap 保存这些寄存器 → 内核读 a7 知道是 write、读 a0-a2 拿到参数 → 处理完把返回值写回 a0 → 恢复寄存器返回用户态。

### 2.5 任务调度：批处理与轮转

> 🤔 **先想**：现在假设你能跑用户程序了。但如果一次只跑一个，跑完才跑下一个，那"多任务"的意义在哪？内核得让多个程序**轮流**用 CPU。你会怎么设计？——每个程序要记录什么状态？什么时候切换？切换时 CPU 要做哪些事？

内核要让多个程序"同时"跑（实际是轮流跑）。本实验用的是**简单的批处理/轮转调度**：

```mermaid
graph LR
    A["App 0 Ready"] -->|"运行"| B["App 0 Running"]
    B -->|"exit/时间片到"| C["标记 Exited"]
    C -->|"选下一个 Ready"| D["App 1 Running"]
    D -->|"...退完"| E["All exited, 关机"]

    classDef ready fill:#e1f5ff,stroke:#0288d1;
    classDef run fill:#fff3e0,stroke:#ef6c00;
    classDef done fill:#e8f5e9,stroke:#2e7d32;
    class A ready;
    class B,D run;
    class C,E done;
```

- 每个任务用一个 **TaskControlBlock（TCB）** 记录它的状态（`Ready`/`Running`/`Exited`，**没有** `Suspended`）、TrapContext、用户栈、内核栈，以及预留给 lab3+ 的 `user_token`。这就是你"如果要设计会怎么记"的答案——内核为每个程序存一份它的全部上下文。
- 当前任务调用 `exit` 或 `yield`，调度器选下一个 Ready 的任务运行。
- 所有任务都 Exited 时，内核关机。

> ⚠️ **本实验的已知限制**：当前调度器是批处理式的——`yield` 在某些情况下可能只触发一次切换就继续往下走到 `exit`。这是简化实现的取舍，不影响理解 trap 机制本身。完整的抢占式调度在后续实验/扩展中补全。看到 `Yield round` 只输出一次时不要困惑，这是已知的。

## 六、思考题与参考答案

### 习题 1

**`trap.asm` 里 `csrrw sp, sscratch, sp` 这一步为什么必须在最前面？**

参考答案：这一步同时完成两件事——把当前 `sp`（用户栈指针）存进 `sscratch`，把 `sscratch` 里保存的内核栈指针装入 `sp`。必须在最前面，因为后续所有"保存寄存器到栈"的操作（`sd x1, 1*8(sp)` 等）都依赖 `sp` 已经指向内核栈。如果先保存寄存器再换栈，就会写到用户栈里，破坏用户数据甚至访问非法地址导致崩溃。

### 习题 2

**`TrapContext` 为什么要保存这么多？漏保存 `sepc` 会怎样？**

参考答案：用户程序随时可能被 trap 打断，打断时它的全部状态（32 个通用寄存器 + 当前的特权级状态 `sstatus` + 下一条指令地址 `sepc`）都必须完整保存，否则返回后没法精确恢复执行。`sepc` 记录"trap 发生时用户程序的 PC"，漏保存会导致 `sret` 返回到错误地址——程序跳到不可预测的位置执行，必然崩溃。

### 习题 3

**处理 `SYS_WRITE` 时为什么要先 `cx.advance_sepc()`？**

参考答案：`ecall` 触发 trap 后，`sepc` 指向 `ecall` 这条指令本身。如果返回时不把 `sepc` 加 4（跳到下一条指令），`sret` 后 CPU 会重新执行同一个 `ecall`，陷入死循环——用户程序永远卡在系统调用上。所以 `advance_sepc()` 在处理逻辑之前调用，保证返回后从 `ecall` 的下一条指令继续。

### 习题 4

**用户态 `sys_write` 的参数怎么传到内核？**

参考答案：按 RISC-V Linux ABI 约定，用户程序把 `fd` 放 `a0`、`buf` 指针放 `a1`、`len` 放 `a2`、syscall 号 64 放 `a7`，执行 `ecall`。trap 后这些寄存器被 `__alltraps` 保存进 TrapContext 的 `x[]` 数组（a0=x10、a1=x11、a2=x12、a7=x17）。内核的 `trap_handler` 通过 `cx.syscall_arg(0/1/2)`（取 x10/11/12）和 `cx.syscall_id()`（取 x17）把这些值取出来，传给 `sys_write(fd, buf, len)`。这就是"用户态寄存器 → TrapContext → 内核函数参数"的传递链路。

### 习题 5

**为什么用户栈和内核栈要分开？**

参考答案：隔离与安全。用户栈在用户地址空间，用户程序可以随意写它；内核栈在内核地址空间，用户程序碰不到。如果合成一个栈：① 用户程序的 bug（栈溢出）会破坏内核数据；② 内核处理 trap 时往用户栈写，可能写到非法地址（用户栈可能没映射）；③ 没法实现特权级隔离（后续 lab3 的虚存会把内核/用户地址空间彻底分开）。分开后，trap 时切到内核栈，内核有自己安全的栈空间，互不干扰。
