# 新手操作指南

这页只回答一个问题：**第一次做 Lab 时，我应该看什么、在哪里动手、怎样判断自己真的完成了？**

## 先记住这一句话

在实验工作台里：

- **左边看手册**：目标、背景、任务、思考题和本 Lab 的提示。
- **右边上方改代码**：在代码工作区打开文件、编辑并保存。
- **右边下方运行和看证据**：终端、Problems、测试结果；学习支持区还有实验报告、学习评价和 Trace。
- **右下角问 AI 导师**：导师帮助你定位和思考，不代替你写代码，也不会因为一句“退出码 0”就判定实验完成。

你不需要另外创建一条“学习链路”。Lab 的顺序、手册、验证、报告和下一层解锁，都在当前工作台里完成。

## 第一次进入前

1. 阅读[认识 os-lab](/guide/start)，了解 Lab1–Lab8 的顺序和它们与 OSTEP 的对应关系。
2. 如果本机还没有工具，按[环境安装](/setup/environment)准备 Rust、RISC-V 目标和 QEMU。
3. 从[引导式学习](/guide/ai-tutor)进入工作台，或者直接打开当前已开放的 Lab，例如 [Lab1 工作台](/learn/lab1)。
4. 只做教师已经开放、并且你已经领取的 Lab。后续 Lab 被锁定时，不是页面坏了，而是前一层的可信验证或复盘尚未完成。

## 工作台各区域做什么

| 位置 | 你会看到 | 你应该在这里做什么 |
| --- | --- | --- |
| 左侧 | 实验手册 | 先读目标和任务，再对照代码；选中一小段文字后可点“就此询问导师”。 |
| 右侧上方 | 代码工作区 | 打开任务要求的文件，修改自己的实现，保存后再运行。 |
| 右侧下方“终端” | 命令输入和输出 | 执行手册给出的验证命令，观察完整输出和错误信息。 |
| 右侧下方“Problems” | 编译诊断 | 查看文件、行号、级别和诊断摘要；点击条目可跳回代码位置。 |
| 右侧下方“测试结果” | 可信运行的断言 | 看期望值、实际值和关键断言；这是判断验证是否通过的主要位置。 |
| 学习支持“Trace” | 运行产生的事件 | 查看 trap、任务切换等真实事件；没有真实 trace 时会显示空状态，不会播放假动画。 |
| 学习支持“实验报告” | 模板或 Markdown 编辑器 | 写过程、证据、思考题和复盘，预览后提交给老师。 |
| 右下角 AI 导师 | 对话窗口和证据条 | 先附上证据，再提具体问题；发送前仍由你决定是否提交。 |

## 一次 Lab 的完整流程

### 1. 先读“要证明什么”

打开当前 Lab 的手册，先找这几部分：

- **学习目标**：本次要理解哪个操作系统机制。
- **前置知识**：需要先看 OSTEP 的哪一部分，或需要已经完成哪个 Lab。
- **任务一/环境准备**：如何启动项目、需要哪些工具。
- **任务二及后续任务**：要读哪些源码、实现什么行为、回答哪些问题。
- **验证与思考题**：最后必须用什么输出或断言证明自己的实现。

阅读时先写下自己的预测，例如“这次系统调用会怎样进入内核”“两个任务应该以什么顺序输出”。预测是后面判断输出是否合理的依据。

**读完这一阶段的反馈**：你应该能用一两句话说出“本 Lab 要实现的机制”和“什么现象可以证明它工作了”。如果只能复述任务标题，还没有进入代码阶段。

### 2. 在代码工作区定位任务文件

按照手册列出的文件打开源码。常见的做法是：

1. 先看入口或调用方，弄清楚数据从哪里来。
2. 再看待补全的函数和附近的结构体、常量。
3. 最后对照用户程序、测试断言或日志，确认实现需要满足什么行为。

代码工作区里的文件状态用于提醒你哪些文件新增、修改或有冲突。不要为了“让列表变干净”删除系统自动生成的文件；先看手册和状态提示。

**完成这一阶段的反馈**：你应该知道至少一个准备修改的文件、一个调用它的路径，以及一个可以观察到的外部结果。

### 3. 修改并保存

在右侧编辑器中完成代码修改，保存后再运行验证。保存本身不会代表实验完成，它只是让工作台和服务端拿到最新内容。

如果 Problems 立刻出现语法、类型或借用错误，先处理这些错误，再进行运行验证。点击 Problems 条目可以回到对应文件和行号。

**完成这一阶段的反馈**：Problems 中不再有阻塞当前构建的错误，或者你已经明确知道这些诊断与当前任务无关，并能解释原因。

### 4. 运行可信验证

优先使用当前 Lab 手册“验证”部分给出的命令。通常：

```powershell
# Lab1–Lab5 的常见形式
cargo run -p kernel --features labN --release

# Lab6–Lab8 的常见形式（需要 VirtIO / fs.img）
make test-labN
```

把 `labN` 换成当前实验编号。Lab6–Lab8 不要擅自改用裸 `cargo run`，因为这些实验需要手册命令准备的 VirtIO 磁盘环境。若手册给出了不同的命令，以手册为准。

**运行后的反馈按这个顺序看**：

1. 终端是否完整结束，是否出现启动、测试或断言输出。
2. 测试结果页是否有当前这次运行的断言，以及“期望值 / 实际值”。
3. 是否生成了可查看的 Trace。
4. Problems 是否有与本次运行关联的编译或诊断信息。

请不要只看“退出码 0”。程序可能正常退出，却没有跑到关键路径，或没有满足关键断言。只有真实的断言、输出和必要的 trace 共同支持你的结论，才算可信证据。

### 5. 失败时先排查，再问导师

建议按以下顺序排查：

1. 当前目录是否是仓库中的 `os-lab`，环境脚本是否已激活。
2. 命令中的 feature 是否与当前 Lab 一致。
3. Lab6–Lab8 是否使用了 `make test-labN`，以及 `fs.img` / VirtIO 前置条件是否满足。
4. Problems 的第一条错误是否指出了真正的编译原因；后面的错误可能只是连锁反应。
5. 测试结果中的第一条失败断言，期望值和实际值分别是什么。

然后再打开 AI 导师。好的提问包含三件事：**你的判断、真实证据、你希望导师帮助判断的一个问题**。例如：

> 我判断 `yield` 返回后应该切换到下一个任务。测试结果中 `Yield round` 只出现 3 次，期望是 5 次；Trace 里有 `trap_enter`，但没有 `task_switch`。请帮我根据这两条证据判断，应该先检查 trap 返回还是调度查找？不要直接给我完整实现。

### 6. 用证据向 AI 导师提问

可以附上的证据和用途如下：

| 证据 | 适合问什么 |
| --- | --- |
| 手册选段 | 不理解某个术语、任务要求或约束。选中一小段后点“就此询问导师”，只会附上选中的文字。 |
| 代码选区 | 某个函数的控制流、类型或边界条件。 |
| 终端选区 | 某一段启动日志、panic 或测试输出。没有选区时才考虑附上本次完整输出。 |
| Problems 条目 | 编译错误的文件、行号和诊断摘要。 |
| 测试结果断言 | 期望值与实际值不一致时，定位行为差异。 |
| Trace 事件 | 解释 trap、task switch 或其他运行时事件的先后关系。 |

附件会先显示在输入框上方，发送后保留在消息气泡中，点击附件可以回到原来的代码行、终端、断言、手册选段或 Trace 位置。附件不会自动发送，也不会把整章手册塞进对话。

### 7. 再次运行并确认结果

根据自己的判断修改代码后，重新保存并执行同一条可信验证命令。对比这次运行与上一次的断言、输出和 trace：

- **通过**：关键断言满足，外部行为符合手册目标，且你能解释为什么。
- **部分通过**：有些输出正确，但关键断言或必要事件缺失；继续定位，不要提前提交。
- **失败**：先记录第一条失败断言和相关证据，再回到代码或向导师提问。

### 8. 完成实验报告

进入学习支持区的“实验报告”页。可以使用教师提供的模板，也可以切换到 Markdown 自由编写。至少写清楚：

1. **我做了什么**：修改了哪些文件、实现了哪个机制。
2. **我观察到什么**：引用真实终端输出、断言或 Trace，不要只写“运行成功”。
3. **我如何判断**：说明证据如何支持你的结论，或哪里仍未验证。
4. **我遇到什么问题**：写出一次失败、自己的判断、AI 导师的提醒和最终验证。
5. **我学会了什么**：回答手册思考题，并写一个与其他系统机制的迁移或对照。

可以在测试结果或 Trace 中使用“插入报告”，把当前证据放入报告的对应段落，再补充自己的解释。预览看到的内容就是提交内容；提交给老师前请再检查代码、命令、run/trace 引用是否对应同一次实验。

**提交后的反馈**：页面会确认报告已提交，教师端可以看到报告及其证据引用。提交报告不等于自动通过所有断言；如果可信验证未完成，先完成验证再提交或按老师要求说明未完成部分。

### 9. 复盘并进入下一 Lab

完成报告后查看“学习评价”，确认系统记录了哪些过程证据、哪些项目仍显示“未观察到”。根据提示补充验证或复盘。当前 Lab 的可信验证与学习复盘都满足后，下一层才会解锁并可领取。

## Lab 顺序速查

| Lab | 核心问题 | 常见验证入口 |
| --- | --- | --- |
| Lab1 | 裸机如何启动、输出并关机 | `cargo run -p kernel --features lab1 --release` |
| Lab2 | trap、ecall、yield 和多任务如何协作 | `cargo run -p kernel --features lab2 --release` |
| Lab3 | 地址空间、页表和虚存如何隔离 | `cargo run -p kernel --features lab3 --release` |
| Lab4 | `fork`、`exec`、`wait` 如何组织进程 | `cargo run -p kernel --features lab4 --release` |
| Lab5 | 文件、管道和并发访问如何工作 | `cargo run -p kernel --features lab5 --release` |
| Lab6 | 数据如何落到 VirtIO 磁盘文件系统 | `make test-lab6` |
| Lab7 | fd、IPC 和信号如何连接进程 | `make test-lab7` |
| Lab8 | 线程、锁、条件变量和死锁如何处理 | `make test-lab8` |

命令只是速查，最终以当前 Lab 手册中的验证命令和关键断言为准。

## 代码、报告、导师附件的边界

- **代码**回答“系统怎样实现”。它必须能被构建和运行。
- **验证证据**回答“这次运行实际发生了什么”。它来自终端、断言、Problems 和 Trace。
- **实验报告**回答“我怎样理解并证明”。它需要你的解释、判断和复盘。
- **AI 导师附件**只是把你选择的上下文带入对话，方便导师针对证据提问；它不会替你保存代码、自动提交报告或代替可信验证。

把这四类内容串起来，一次 Lab 才算完整：**读懂目标 → 修改代码 → 运行验证 → 解释证据 → 写报告 → 复盘解锁**。

## 仍然卡住时

请保留以下信息再求助：当前 Lab、执行的完整命令、第一条失败信息、测试结果中的期望/实际值、相关代码行，以及你自己的判断。这样导师或老师可以沿着证据回到具体位置，而不是只能猜测“哪里可能有问题”。
