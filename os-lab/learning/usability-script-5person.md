# 5 人可用性最小脚本（成员 A · Day 7）

> 从 `trial-protocol-m5.md` 压缩：本周**可执行**的最短可用性测试。  
> 不替代正式课堂试验；不把结果写成因果结论。

## 1. 目标（只问三件事）

1. 学生能否在 **25 分钟内**走通：领取 Lab2 debug → 改 → 可信运行 → 看 Trace/断言？  
2. 提示阶梯/护栏是否降低「直接要完整代码」，又不过度挫败？  
3. 报告里是否出现「我 / AI / 验证」三分结构（或明确缺哪一块）？

## 2. 人数与角色

| 角色 | 人数 | 说明 |
| --- | --- | --- |
| 学生被试 | 5 | 尽量含：OS 零基础 2、上过 OS 2、助教视角 1 |
| 主持 | 1 | 成员 A 或教师 |
| 观察记录 | 1 | 可兼主持；只记录，不代操作 |

## 3. 会前 10 分钟

- [ ] 测试账号可登录；Lab2 debug 可领取  
- [ ] tutor 服务与可信 recipe 可用  
- [ ] 告知：系统分**不是**最终成绩；可随时停止  
- [ ] 准备纸笔或表格：下节「记录表」

## 4. 任务脚本（每人约 30–40 分钟）

| 时刻 | 动作 | 主持台词（可照读） |
| --- | --- | --- |
| 0:00 | 登录领取 | 「请登录，领取 Lab2 的 debug 任务，打开标成待完成的文件。」 |
| 0:05 | 先跑一次 | 「先不要问 AI 要完整代码。先运行一次，数 Yield round 出现几次。」 |
| 0:10 | 最小假设 | 「用一句话写下假设：为什么只 yield 一次就结束？」 |
| 0:15 | AI 规则 | 「可以问 AI，但先说现象和假设。若它拒答完整代码，请改问区分双栈/调度的方法。」 |
| 0:25 | 修复再跑 | 「改一处你认为对的地方，再跑可信验证。看 Yield 是否 ≥5。」 |
| 0:30 | Trace/报告 | 「若有 Trace，选一帧插入报告；反思里写清：我的判断、AI 提醒、哪次运行证明。」 |
| 0:35 | 主观 3 问 | Likert（1）哪里最卡？（2）AI 有帮助吗？（3）是否想过只看退出码？ |

**超时规则**：25 分钟仍未 verified → 记「未完成」并停止施压；可演示参考路径但不代填报告。

## 6. 会后 20 分钟（主持）

1. 汇总：完成人数、共同卡点 Top3。  
2. 至少写 **3 个失败/摩擦案例**（负担增加 / 误解 / 量规或文案问题）。  
3. 输出半页《可用性修订建议》链到 `progress.md`（改文档/提示/量规哪一条）。  
4. **禁止**写「显著提升学习效果」（n=5 且无对照）。

## 7. 已知局限（写进知情与报告）

| 局限 | 说明 |
| --- | --- |
| 样本量小 | 只发现可用性问题，不能推广到全班成绩 |
| 观察者效应 | 有人盯着时更少直接要答案 |
| 功能未齐 | 若导师证据条/评分 v2 UI 未上线，本脚本仍测主路径，并在记录中注明缺失 |
| 环境差异 | Windows 路径/首次编译耗时会影响「用时」 |
| 变式偏差 | 默认 debug；补救变式需另开一场 |
| 伦理 | 数据脱敏；应要求可删账号学习数据 |
