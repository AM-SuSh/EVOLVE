# Lab2 工作台 UI 文案审核（成员 A · 第 2–3 天）

原则：**先告诉学生「此刻要达成的学习目标」**，再给功能说明。避免「这里有编辑器/终端」盖过「你要证明什么」。

## 建议采用的文案

| 位置 | 现况倾向 | 建议文案（目标向） |
| --- | --- | --- |
| 工作台顶栏 / 当前 Lab | 强调功能名 | `当前目标：跑通用户态 trap，并证明多任务可协作切换` |
| 代码面板标题 | 「系统代码 / 参考实现」 | 有变体时：`你的任务文件 · task.rs（fill/debug）`；参考实现保持只读标签 |
| 终端默认命令旁 | 「恢复默认验证命令」 | `运行受信验证（需同时看到 Hello / 幂结果 / Yield×5 / 全部退出）` |
| 验证通过提示 | 「命令成功」 | `断言通过：输出证据已齐` / 失败时逐条列出缺哪条断言 |
| 导师开场 | 功能引导 | 保持追问式；补一句：`先写你对「用户为何不能直接调内核函数」的判断` |
| 阶段「验证/排错」 | 工具罗列 | `用最小实验区分：双栈错误 vs 调度状态错误 vs ABI 错误` |
| 报告区 | 粘贴输出 | `请写：假设 → 证据（含 Yield 行数）→ 结论；不要只贴退出码` |

## 不要对学生说的话

- 「随便跑一条退出码为 0 的命令就算过」
- 「编辑器支持语法高亮」作为阶段主标题（可放次要说明）
- 在未确认变体前剧透 debug 的具体 bug 行
